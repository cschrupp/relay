## 2. Inherited architecture and constraints

The target Slice-16 roadmap frame requires the UI to remain an adapter/client of the accepted product/backend layer:

```text
Browser UI
   ↓
supported UI/backend interface
   ↓
src/offline_rag/app/
   ↓
domain + infrastructure
```

The accepted Slice-15 product query is server-owned and grounded:

```text
POST /v1/query
request = { corpus, question }
product_mode_id = grounded_v1
```

The existing canonical app-layer use case is `run_product_query(...)`. It:

- validates the product corpus and normalized question;
- resolves and binds the published snapshot;
- executes the grounded query path;
- validates citation provenance;
- returns only `answered`, `insufficient_evidence`, or `model_abstain` as successful product statuses;
- allocates/persists trace identity once execution begins;
- returns the product projection containing corpus, snapshot, product mode, trace, answer/status, and citations.

The existing `/v1/query` adapter already owns query-capacity admission, worker-thread ownership, disconnect cancellation, and operation release.

The repository already includes FastAPI, Uvicorn, `python-multipart`, Pydantic, and HTTPX. No browser/frontend framework is currently required.

## 3. Problem statement

Offline RAG has an accepted product/API boundary but lacks a minimal browser experience demonstrating that capability.

M0 needs a real but bounded feature that proves:

1. a Human-approved design can be converted into an exact implementation result;
2. the implementation can be manually evaluated against evidence;
3. Human technical acceptance and accepted-result provenance remain distinct from test/CI evidence.

The feature must therefore be useful enough to be real product work while remaining small enough that governance, rather than frontend-framework setup, remains the experiment's focus.

## 4. Design decision summary

### D16A-01 — Delivery architecture

**Decision:** use a **same-process, same-origin, server-rendered FastAPI UI**.

```text
Browser
   ↓ GET /ui | POST /ui/query
FastAPI UI adapter
   ↓ canonical owned query execution seam
run_product_query(...)
   ↓
accepted Offline RAG application/domain/infrastructure
```

No SPA and no separate frontend development server are introduced in Slice 16A.

### D16A-02 — Frontend technology

**Decision:** HTML generated by repository-owned Python rendering code plus minimal CSS; **no client-side JavaScript is required** for Slice 16A.

Rationale:

- no Node/npm/Vite/etc. toolchain;
- no CORS design;
- no duplicated client state machine;
- deterministic pytest coverage can verify the rendered answer/abstention/error states;
- no new runtime dependency;
- strong fit with the fully local/offline product objective;
- keeps M0 focused on the already accepted product seam rather than frontend infrastructure.

This is a bounded M0 decision, not a permanent prohibition on a richer later Slice-16 frontend.

### D16A-03 — Product execution seam

**Decision:** the UI must invoke the **same canonical app-layer product query use case** used by `/v1/query`; it must not call the retriever, Qdrant, reranker, generator, snapshot internals, or scientific pipeline directly.

A small HTTP-layer execution helper may be extracted from the existing `/v1/query` adapter so both the JSON API route and the HTML UI route share the same:

```text
runtime readiness
query-capacity admission
owned worker execution
disconnect cancellation
operation release
```

The helper is coordination-only. It must not create a second query semantic contract.

### D16A-04 — UI routes

The bounded HTML surface is:

```text
GET  /ui
POST /ui/query
```

`GET /ui`:

- renders the initial query page;
- performs no product query;
- allocates no query trace;
- does not mutate corpus/product state.

`POST /ui/query`:

- accepts form data containing exactly `corpus` and `question`;
- rejects missing, duplicate, or unexpected query fields;
- constructs/validates the same product request semantics;
- executes the canonical product query seam;
- renders one terminal page state.

The JSON API remains:

```text
POST /v1/query
```

with unchanged request/response semantics.

### D16A-05 — No new product API

`/ui/query` is an HTML transport endpoint, not a new JSON/backend query API.

Slice 16A must not add:

- `/v2/query`;
- alternate query modes;
- algorithm selectors;
- snapshot selectors;
- retriever controls;
- recovery controls;
- backend endpoints created solely to support UI convenience.

### D16A-06 — Page-state model

The renderer owns a small presentation-only state model:

```text
idle
answered
insufficient_evidence
model_abstain
error
```

Presentation state never changes backend scientific meaning.

Conceptual view model:

```text
QueryPageState
  state
  corpus
  question
  answer?
  citations[]
  trace_id?
  snapshot_id?
  product_mode_id?
  error_code?
  error_message?
  retryable?
```

The view model is not persisted and is not a new domain model.

### D16A-07 — Answer behavior

For `answered`:

- render the exact returned answer as text;
- render at least one returned validated citation;
- do not infer citation text or source attribution not returned by the product response;
- expose `trace_id`;
- expose `snapshot_id` in a provenance/details area;
- optionally expose `product_mode_id` as diagnostic provenance.

### D16A-08 — Citation presentation

Each citation is rendered from the existing public citation projection only:

```text
evidence_unit_id
document_id
source_chunk_id
kind
section_path
page_start
page_end
line_start
line_end
clipped
```

Slice 16A does not require document-content preview or new source-fetch APIs.

Human-readable rendering may omit empty location fields but must preserve returned source identity.

No browser-side citation reconstruction is allowed.

### D16A-09 — Abstention behavior

For `insufficient_evidence`:

- render an explicit “insufficient evidence” result;
- render no generated answer;
- render no invented citation.

For `model_abstain`:

- render an explicit model-abstention result;
- render no generated answer;
- render no invented citation.

These two statuses remain visibly distinguishable.

### D16A-10 — Error behavior

Product/application failures render a dedicated error state, never an answered state.

The UI may show only information from the canonical safe product error envelope, principally:

```text
error code
safe message
retryable
trace_id when present
```

The UI must not display Python exception text, stack traces, paths, secrets, request headers, model-provider internals, or raw unsanitized detail mappings.

Where an `AppError` has a normative HTTP status, the HTML response should preserve that status instead of converting every error to HTTP 200.

A disconnected/cancelled browser request must preserve the existing worker-ownership/cancellation semantics and must not release query capacity before the worker terminates.

### D16A-11 — Form/input behavior

The UI provides:

```text
corpus: required text input
question: required textarea
```

The question control should expose the existing 8,000-character maximum as a browser hint/constraint while server validation remains authoritative.

On a rendered terminal result or error, the submitted corpus/question may be redisplayed for user context, but all redisplayed values must be HTML-escaped.

No additional product/scientific input is permitted in Slice 16A.

### D16A-12 — XSS and HTML safety

All externally influenced values are untrusted presentation data, including:

- question;
- corpus;
- generated answer;
- citation identities/paths;
- safe error message/code;
- trace/snapshot/product-mode identity.

They must be rendered as escaped text, never interpolated as trusted markup.

Repository-owned static markup/CSS may be emitted directly.

No model-generated HTML is interpreted.

### D16A-13 — Browser security headers

HTML responses should set bounded defensive headers appropriate for the no-JavaScript design, at minimum:

```text
Content-Type: text/html; charset=utf-8
Cache-Control: no-store
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Content-Security-Policy:
  default-src 'none';
  style-src 'unsafe-inline';
  form-action 'self';
  base-uri 'none';
  frame-ancestors 'none'
```

If implementation eliminates inline CSS, `style-src 'self'` may replace `'unsafe-inline'` without requiring redesign.

No external fonts, analytics, CDN assets, scripts, or network dependencies are authorized.

### D16A-14 — Network/bind boundary

The UI is mounted on the existing FastAPI application and therefore inherits the existing server bind policy.

Default product serving remains loopback-only unless the user explicitly enables the existing non-loopback override.

Slice 16A does not introduce auth/RBAC, TLS termination, public deployment, or a separate listening socket.

### D16A-15 — Runtime ownership

The UI must not construct a second `ApplicationRuntime`, query runtime cache, model runtime, or resource pool.

It uses `request.app.state.runtime`, exactly as the API adapters do.

Application startup/drain ownership remains the existing FastAPI lifespan.

### D16A-16 — Query concurrency and cancellation

The HTML route must preserve existing query operation ownership:

```text
runtime.require_ready()
operation = runtime.operations.admit_query()
run_owned_worker(... watch_disconnect=True ...)
runtime.operations.release(operation) in finally
```

Implementation may centralize this sequence into a private API-layer helper shared with `/v1/query`.

It must not:

- bypass capacity admission;
- spawn detached/background query work;
- release capacity before worker termination;
- introduce a second timeout/cancellation model.

### D16A-17 — JSON API compatibility

Existing `/v1/query` behavior is a regression boundary.

The implementation must prove that the refactor/addition leaves intact:

- request schema;
- extra-field rejection;
- success response shape;
- error envelope/status mapping;
- disconnect behavior;
- capacity ownership;
- trace semantics.

No accepted Slice-15 product response field may be removed or reinterpreted.

### D16A-18 — Dependency/build policy

Expected dependency delta:

```text
runtime dependency changes: NONE
dev dependency changes: NONE
Node/npm/frontend build tool: NONE
external CDN/runtime asset: NONE
```

Existing `python-multipart` supports HTML form parsing.

A dependency addition is a design-stop condition requiring explicit review; it must not be silently introduced during implementation.

### D16A-19 — Static asset policy

For this minimal slice, prefer repository-owned Python-rendered HTML with embedded bounded CSS so no package-data/static-asset pipeline is required.

If implementation discovers a compelling reason to add separate packaged CSS, that remains acceptable only if:

- it is local/offline;
- wheel/container packaging is deterministic;
- no frontend build system is added;
- tests prove the asset is available from the installed/package runtime.

No JavaScript asset is required by the accepted design.

### D16A-20 — Accessibility/minimum UX

The UI is intentionally small but should include:

- explicit `<label>` elements for corpus and question;
- semantic heading structure;
- submit button text that describes the action;
- readable status heading for answer/abstention/error;
- citations as semantic list/definition content;
- visible keyboard focus using browser defaults or repository CSS;
- no color-only status distinction.

No component library is required.

## 5. Request / execution flow

### Initial page

```text
Browser
  -> GET /ui
  -> HTML form
  -> no runtime query / no trace
```

### Query

```text
Browser
  -> POST /ui/query {corpus, question}
  -> strict form projection
  -> existing request semantics
  -> existing ApplicationRuntime
  -> query capacity admission
  -> owned worker
  -> run_product_query(...)
  -> ProductQueryResponse
  -> safe presentation-state projection
  -> escaped HTML
```

### Error

```text
run_product_query / runtime
  -> AppError
  -> canonical safe error projection
  -> error view state
  -> escaped HTML + normative HTTP status
```

No retrieval/generation object is exposed to the HTML layer.

## 6. Proposed implementation structure

The exact implementation may make small naming adjustments without redesign, but the expected bounded production surface is:

### New production file

```text
src/offline_rag/api/ui.py
```

Responsibilities:

- `/ui` and `/ui/query` router;
- strict form projection;
- presentation-only page-state construction;
- HTML escaping/rendering;
- UI security headers;
- invocation of shared canonical query execution seam.

### Existing production files allowed to change

```text
src/offline_rag/api/app.py
src/offline_rag/api/query.py
```

`app.py`:

- register the UI router only.

`query.py`:

- only the minimum internal refactor required to share owned query execution between `/v1/query` and the UI route;
- public `/v1/query` contract unchanged.

### Tests

Expected new tests may include:

```text
tests/unit/api/test_ui.py
```

If repository test organization does not currently use `tests/unit/api/`, an equivalent bounded path is acceptable.

Existing `/v1/query` tests may be updated only as required to demonstrate unchanged behavior after helper extraction.

### Documentation

A narrow Slice-16A implementation/acceptance note may later update the target project's Slice-16 documentation after implementation acceptance. It is not required to mutate roadmap claims before technical acceptance.

## 8. Deterministic verification plan

Implementation evaluation must include deterministic tests for the following.

### V16A-01 — Initial page

`GET /ui`:

- 200 HTML;
- form contains exactly the supported product inputs (`corpus`, `question`) plus submit control;
- form targets `/ui/query` with POST;
- no query executed;
- no trace created by page load.

### V16A-02 — Answered rendering

Given a controlled canonical `ProductQueryResponse(status="answered")`:

- returned answer text appears;
- citation identities/provenance appear;
- trace ID appears;
- snapshot ID appears;
- state is visibly answered.

### V16A-03 — Insufficient evidence

Given `status="insufficient_evidence"`:

- explicit insufficient-evidence state appears;
- no fabricated answer appears;
- no fabricated citation appears;
- trace/snapshot provenance remains available.

### V16A-04 — Model abstention

Given `status="model_abstain"`:

- explicit model-abstention state appears;
- no fabricated answer/citation appears;
- it is distinguishable from insufficient evidence.

### V16A-05 — Error rendering

Given representative `AppError` cases:

- safe code/message rendered;
- normative HTTP status preserved;
- retryability may be shown;
- trace ID rendered when present;
- internal exception/secret material not rendered.

Representative cases should include at least request invalidity plus one runtime/provider failure.

### V16A-06 — Input contract

Tests prove:

- only `corpus` and `question` are accepted as query data;
- missing/empty question fails;
- over-limit question fails;
- unexpected form fields fail;
- duplicate query fields fail or are deterministically rejected;
- server-side validation remains authoritative.

### V16A-07 — Escaping/XSS

Adversarial values containing HTML/script-like text in at least:

- question;
- answer;
- citation field;
- safe display identity

must appear escaped and must not be emitted as executable markup.

### V16A-08 — Security headers

HTML responses include the accepted no-store/nosniff/referrer/CSP policy.

### V16A-09 — Canonical seam

Tests prove the UI adapter reaches the canonical query execution seam and does not directly construct/call retriever, Qdrant, reranker, or generator objects.

This may be demonstrated by controlled `ApplicationRuntime`/query-use-case doubles and import/change-surface inspection.

### V16A-10 — `/v1/query` regression

Existing API tests remain green and focused regression tests prove unchanged JSON request/response/error behavior after any helper extraction.

### V16A-11 — Owned-worker semantics

The UI route preserves query capacity ownership and release even on:

- success;
- application error;
- task cancellation/disconnect where testable under the existing worker helper seams.

### V16A-12 — Offline/no-new-dependency boundary

Evidence must show:

```text
pyproject runtime dependencies unchanged
pyproject dev dependencies unchanged
no package-lock/npm/yarn/pnpm frontend manifest introduced
no CDN/external asset reference introduced
```

## 9. Local smoke evidence

In addition to deterministic tests, implementation evaluation should capture one practical local browser/demo run against the accepted product stack when the local model/corpus environment is available:

```text
open /ui
submit corpus + question
observe terminal answer OR legitimate abstention
observe citation/provenance when answered
record exact implementation SHA
record trace_id
record snapshot_id
```

The smoke run supplements tests; it does not replace them.

If the real model environment is unavailable during implementation, that is recorded as an evidence limitation rather than replaced by a fabricated success claim.

## 10. Acceptance criteria

The implementation is eligible for evaluator `ACCEPT` only if all of the following are true:

1. target implementation starts from the governed frozen baseline or a later explicitly re-authorized baseline;
2. browser query experience is usable through `/ui`;
3. only corpus/question product inputs are exposed;
4. canonical product query semantics are reused;
5. answered/insufficient/model-abstain states render correctly;
6. citations are rendered only from validated returned provenance;
7. trace and snapshot provenance are available;
8. product errors are visibly distinct from successful states;
9. untrusted/model text is HTML-escaped;
10. existing API behavior remains unchanged;
11. no new runtime/dev/frontend dependency is introduced;
12. no scientific/backend scope expansion occurs;
13. deterministic tests cover V16A-01 through V16A-12 to the extent applicable to the repository's existing test seams;
14. repository quality gates pass;
15. any local smoke limitation is explicitly disclosed rather than hidden.

## 11. Required quality gates

Implementation should run the repository's canonical quality gates at the candidate SHA. At minimum:

```text
uv sync --frozen --group dev
uv run ruff format --check .
uv run ruff check .
uv run pytest
```

If the target repository has additional canonical gates at implementation time, the implementation handoff must include them rather than silently omitting them.

No new quality tool is authorized by this design.

## 12. Design stop conditions

Stop and return to Human Authority/design review if implementation would require any of:

- changing `/v1/query` semantics;
- changing accepted product statuses;
- changing citation semantics;
- new backend query endpoint;
- new runtime dependency;
- new dev dependency/toolchain;
- Node/npm frontend build;
- direct UI access below the application/product layer;
- new scientific tuning control;
- authentication/RBAC redesign;
- public/cloud deployment work;
- second runtime/service/process;
- Slice 16B+ scope;
- unrelated backend refactor beyond the minimal shared execution seam;
- movement from the frozen target baseline that changes relevant query/UI assumptions without explicit rebasing authority.

## 13. Deferred capability

This design deliberately leaves for later separately governed work:

- rich document preview;
- retrieval/evidence inspector;
- corpus/document management UI;
- ingestion UI;
- benchmark/evaluation visualization;
- architecture/portfolio-polish pages;
- client-side interactivity beyond standard HTML forms;
- richer SPA frontend.

Those are not defects in 16A; they are outside this M0 contract.

## 14. Design conclusion

The selected architecture is intentionally conservative:

```text
one existing FastAPI process
+ one HTML adapter
+ one canonical query use case
+ no JS framework
+ no new dependency
+ no scientific change
```

It is sufficient to make Offline RAG demonstrably usable from a browser while preserving the accepted product boundary and providing a strong, deterministic subject for Relay's Phase-1 manual governance validation.
